# Coding Standards: Stochastic Process Visualizer

## 1. Общие принципы
- **Читаемость важнее краткости** – код пишется для людей, а не только для машин.
- **Явное лучше неявного** – избегаем магии, неявных преобразований, глобального состояния.
- **Единообразие** – любой участник команды должен понимать любой участок кода без переключения стилей.

## 2. Бэкенд (Python 3.11+, FastAPI)

### 2.1 Форматирование кода
- Используется **Ruff** с правилами, эквивалентными Black + isort + flake8.
- Отступы – **4 пробела** (никаких табуляций).
- Максимальная длина строки – **88 символов**.
- Пустые строки: одна между методами класса, две между функциями на верхнем уровне.

### 2.2 Именование
| Тип | Стиль | Пример |
|-----|-------|--------|
| Переменные и функции | `snake_case` | `process_type` |
| Классы | `PascalCase` | `WienerProcess` |
| Константы | `UPPER_SNAKE_CASE` | `MAX_N` |
| Приватные | `_leading_underscore` | `_validate()` |

### 2.3 Типизация
- Обязательна аннотация типов для всех аргументов и возвращаемых значений.
- Используем `mypy` для проверки.

### 2.4 Структура бэкенд-проекта
backend/
├── app/
│ ├── main.py
│ ├── models.py
│ ├── processes.py
│ ├── validation.py
│ └── utils.py
├── tests/
└── requirements.txt

### 2.5 Обработка ошибок
- Запрещены голые `except:`.
- В FastAPI – `HTTPException` с кодом 400/500.
- Собственные исключения наследуются от `Exception`.

### 2.6 Асинхронность (бэкенд)
- Эндпоинты FastAPI объявляем как `async def`.
- Для CPU-bound задач (генерация траекторий) допустим прямой вызов синхронных функций; при необходимости – `run_in_executor`.

## 3. Фронтенд (ES2020+, HTML5, CSS3, без сборки)

### 3.1 Структура фронтенда

├── index.html # единственная страница
├── css/

├── js/

### 3.2 HTML стандарты
- Семантические теги (`<main>`, `<section>`, `<button>`, `<label>`, `<input>`).
- `<label>` с `for` или обёртка.
- Атрибуты `aria-label` для интерактивных элементов без текста.
- Валидный HTML5.

### 3.3 CSS стандарты
- **Именование классов**: `kebab-case` (например, `generate-button`, `parameter-panel`).
- **Методология**: БЭМ (опционально, но приветствуется).
- **Адаптивность**: через `@media (min-width: ...)`.
- **Запрещено**: использование `!important` без крайней необходимости, ID для стилизации.
- **Отступы**: 2 пробела.
- **Максимальная длина строки**: 100 символов.

### 3.4 JavaScript стандарты
- **Отступы**: 2 пробела.
- **Точка с запятой**: обязательна в конце каждого выражения.
- **Кавычки**: одинарные для строк, двойные только для JSON и атрибутов HTML.
- **Именование**:
  - Переменные и функции: `camelCase` (например, `processType`, `generateTrajectory`).
  - Константы (глобальные): `UPPER_SNAKE_CASE` (`API_ENDPOINT`).
  - Обработчики событий: `handle` + событие + элемент (`handleGenerateClick`).
- **Объявление переменных**: `const` по умолчанию, `let` только для переприсваивания, `var` запрещён.
- **Сравнение**: строгое равенство `===` и `!==`.
- **Модульность**: использовать IIFE или `script type="module"` для изоляции глобального пространства.
- **Кеширование DOM**: все часто используемые элементы сохраняются в переменные.
- **Обработка ошибок**: `try..catch` вокруг всех асинхронных операций (fetch, JSON.parse).
- **Длина функции**: не более 50 строк – разбивать на подфункции.
- **Валидация**: клиентская валидация параметров (дублирует бэкенд для UX).

### 3.5 Работа с API (фронтенд)
- Использовать `fetch()` с `async/await`.
- Базовый URL выносить в константу `API_BASE`.
- Проверять `response.ok`, иначе бросать ошибку.
- Показывать пользователю человеко-читаемые сообщения об ошибках.

```javascript
const response = await fetch(`${API_BASE}/generate`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload)
});
if (!response.ok) {
    const error = await response.json();
    throw new Error(error.detail || 'Generation failed');
}

### 3.6 Доступность (A11y) на фронтенде
Все интерактивные элементы доступны с клавиатуры (естественный tabindex, видимый фокус).

Использовать <button>, а не <div onclick>.

Для графиков Plotly – добавлять aria-label и текстовое описание.

## 4. Документирование кода
### 4.1 Бэкенд (Python docstrings)
Формат: Google или NumPy – единый для всего проекта.

Обязательно для: всех публичных функций, классов и модулей.

Содержит: описание, параметры (Args:), возвращаемое значение (Returns:), примеры (Example:).

### 4.2 Фронтенд (комментарии в JavaScript)
Комментировать: неочевидные DOM-манипуляции, сложные алгоритмы (например, преобразование Бокса–Мюллера).

В начале файла app.js: краткое описание модуля (что делает, как устроен).

Запрещено: оставлять закомментированный код – удаляем через Git.

## 5. Git и коммиты
Сообщения коммитов: на английском, в формате type(scope): short description (Conventional Commits).

feat(api): add Ornstein-Uhlenbeck endpoint

fix(frontend): validate N before sending request

docs(readme): update setup instructions

Один коммит – одна логическая единица (не смешивать исправление ошибки с новым функционалом).

Ветки: main – production-ready, develop – интеграционная (опционально для MVP), feature-ветки от develop.

## 6. Комментарии в коде (общие правила)
Не комментировать очевидное – код должен быть самодокументируемым через понятные имена.

Комментировать "почему" – объяснять причину неочевидного решения, а не "что" делает код.
